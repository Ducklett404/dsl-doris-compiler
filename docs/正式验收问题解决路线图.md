## 2. 阶段一：完善项目侧规则和测试

优先级：最高。主要负责人：项目开发者，可直接推进。

### 2.1 为资金字段确定明确的缺失值规则

当前差异是：旧断言要求直接读取 `ZJLXMainNetTur`，当前实现使用 `NULLIF(ZJLXMainNetTur,-999999)`。

实施步骤：

1. 对照字段字典、现有注册表、语义视图和参考 SQL，记录该字段的单位、有效值范围、NULL 含义及哨兵值约定。
2. 区分“项目当前采用的规则”和“官方已经确认的规则”。如果官方尚未确认 `-999999` 对这个具体字段的含义，将其列为待确认项。
3. 新增独立的小型测试数据，覆盖正常正数、正常负数、0、NULL、`-999999`、缺少衍生行和窗口有效值不足。
4. 根据字段规则手工确定预期结果，再分别运行参考实现与生成 SQL。

判断分支：

| 核实结果 | 处理 |
|---|---|
| 该字段明确以 `-999999` 表示缺失 | 保留字段级 NULL 转换，使新版本参考计算与结构要求遵守同一规则 |
| 该字段允许 `-999999` 作为正常数值 | 修正该字段的转换逻辑，并验证合法负值不会被吞掉 |
| 规则仍不明确 | 保留诊断能力及待确认状态，不能把该行为宣称为已获官方认可 |

不能把所有负数都当成缺失值，也不能把某个字段的哨兵约定直接推广到所有数值字段。

### 2.2 发布新的测试基线

在规则明确后，处理两项黄金结构失败：

1. 保留原冻结黄金集和原始失败报告。
2. 新建带版本号的测试基线，说明字段规则、结构断言及必要的参考计算变更；版本号在实施时确定。
3. 预期结果必须来源于规则和独立计算，不能依据编译器当前输出反推。
4. 结构检查覆盖关联键、字段、过滤、排序、参数绑定和缺失值行为；避免仅因无语义影响的 SQL 排版差异失败。
5. 复跑原有用例、新增边界数据及真实 Doris 对比。内部已经可见的用例不能替代官方保管的外部盲测。

**完成标准：**规则、编译器、参考实现与新测试基线一致；每项变更有原因、版本和测试证据。不能仅删除两条失败断言就宣布完成。

## 3. 阶段二：定位跨表关联问题

优先级：最高。项目侧可以继续定位，最终处理依赖数据提供方说明。

当前关联键为 `(mktcode, tgtcode, bizdate)`。未关联的 249,480 条衍生记录约占衍生表的 4.04%；其中最新日仍有 48 条。179,507 条所在的市场、日期在基础表中完全没有记录，值得优先核实文件覆盖及日期含义。

### 3.1 先排查项目读取和映射

- 确认是否收到完整文件包，是否存在增量文件、补丁文件、不同批次或额外目录。
- 对照官方说明确认市场枚举、证券代码格式和两张表的日期含义。
- 检查代码前导零、空白字符、编码及日期转换是否改变了关联键。
- 选择同一证券的连续记录，核对异常日前后的基础与衍生数据；按证券基础历史跨度、市场和日期分类解释异常。

目前全量类型检查和主键检查通过，两个数据库也复现了相同未关联数量，因此没有证据支持直接归因于某一个查询引擎。但仍需要字段定义来验证关联规则是否合理。

### 3.2 根据官方答复选择处理路线

| 路线 | 适用条件 | 实施动作 | 完成标准 |
|---|---|---|---|
| A：补齐数据 | 官方确认缺少基础行情或漏发文件 | 保存原包，接收补丁，按官方说明处理增量、重复及更正记录，生成新快照 | 新快照满足已确认的关联规则；差异可追溯 |
| B：修正关联映射 | 官方确认市场、证券或日期字段采用不同口径 | 建立有依据的映射；检查映射唯一性和有效期；调整关联及参考实现 | 映射前后有对照，避免一对多误配及未来数据泄漏 |
| C：明确允许独立记录 | 官方确认某些衍生记录可以没有基础行情 | 定义允许条件、证券筛选基准表、缺失值及窗口计算规则，发布新的契约与门禁版本 | 所有例外均符合可检查的规则；不满足条件的异常仍失败 |
| D：暂时无法确认 | 官方尚未答复或说明不足 | 保留全量数据用于诊断，继续项目侧测试并记录不确定项 | 形成待确认清单；正式快照验证继续保持失败 |

推荐先排查 A，再核实 B 和 C。这个顺序用于提高排查效率，不表示已经确定数据缺失。

禁止通过删除 249,480 条记录、随意匹配到前一个交易日、补造基础价格或直接放宽异常比例来获得通过状态。若官方确实规定这些处理方式，应把依据、算法和影响写入新的契约。

- 是否存在字段级缺失标记，当前程序尚未识别。

| 官方结论 | 处理 |
|---|---|
| 明确是错误数据 | 获取更正数据，生成新快照并重跑检查 |
| 字段定义不同 | 更新字段映射和质量检查，使比较针对同一口径 |
| 是有明确条件的合法例外 | 编写条件化检查，并保留例外计数和样例 |
| 无法解释 | 保留警告，在验收材料中明确其影响 |

**完成标准：**异常被更正，或有规则能够解释其合法性。不能把收盘价强行截断到最高价与最低价之间。

## 5. 阶段四：建立可验证的新快照

前置条件：影响硬性门禁的数据及规则问题已经明确。

实施顺序：

1. 锁定输入文件、字段规则、关联规则、编译器版本和测试基线。
2. 若数据或语义有变化，创建新的快照/契约版本，保留旧版本证据；重新计算文件哈希、行数、日期范围及字段统计。
3. 将新快照导入独立测试实例，核对所有加载响应、加载行数、过滤行和未选中行。
4. 验证复合主键、日期覆盖、跨表关联、类型、单位及缺失值规则。
5. 重建依赖该快照的特征表，核对 MA 等特征与明细参考结果一致。
6. 只有该版本规定的硬性检查全部通过后，才登记 `VALIDATED`。

实现提示：当前部分诊断脚本固定了旧快照日期、行数、用例数或报告目录。切换新快照前，应把这些值改为读取显式配置或 manifest，并检查所有引用的版本相互匹配，避免把正确的新数据误判为失败，或错误复用旧参考结果。

当前正式执行接口依赖已验证快照。诊断查询成功不会自动解除这一限制。

## 6. 阶段五：完成统一验收

按以下顺序推进，避免在数据与结果仍不稳定时解释性能结果。

| 顺序 | 验证内容 | 完成标准 |
|---|---|---|
| 1 | 单元、语义、编译与执行回归 | 必需检查通过；跳过项逐项说明原因和后续安排 |
| 2 | 新版本黄金集 | 语义、SQL 结构、结果三层均符合约定 |
| 3 | 边界数据 | 缺失值、合法负数、历史不足、新股、观察间隔、并列排名等有独立预期 |
| 4 | 真实数据对比 | 在同一快照上比较完整证券集合；排序查询比较完整顺序；数值按约定容差比较 |
| 5 | 正式接口与权限 | 在验证快照上检查鉴权、执行权限、只读账号、超时、资源释放及错误响应 |
| 6 | 官方样例和外部盲测 | 使用官方确认的分母、规则与标准答案；当前 34 个诊断用例不能替代这一项 |
| 7 | 性能评测 | 固定硬件、版本、缓存条件、负载和数据快照，分别报告编译与数据库执行性能 |
| 8 | 汇总验收材料 | 工件、配置、命令、结果和限制齐全，可由另一环境复跑 |

项目已有长周期性能矩阵，但实际执行范围应以验收约定为准；大规模冷启动评测需要单独安排时间与资源。当前编译器 P95 不能替代数据库查询延迟。

行业字段全空、类别标志缺乏变化、复权因子恒定等数据限制，也需要明确验收范围。单个函数执行成功或返回空集合，不能证明真实行业、类别及复权业务正确。若这些能力属于必验范围，应补齐具有区分度的数据与标准答案。
